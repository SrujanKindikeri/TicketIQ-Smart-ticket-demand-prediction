# TicketIQ complete cinema booking system

Four-commit implementation adds Payment/BookingSeat models, 13 new API endpoints, 7 React frontend pages, and an 18-test suite on top of the existing Movies/Shows/Dashboard shell. The approach follows an atomic hold-then-pay pattern: seats are locked for five minutes, a booking record is created on hold conversion, and the booking is confirmed only after Razorpay signature verification. When RAZORPAY credentials are absent the system falls into a clearly labelled test-mode path that skips real payment. All 18 tests pass, the Django system check is clean, and the frontend build produces a working bundle.

Watch for: (1) **confirmed** — `RAZORPAY_KEY_SECRET` absent from environment causes HMAC verification to run against an empty string, producing a deterministic HMAC; an attacker who knows the order ID can pre-compute that value and confirm any real Razorpay order without paying. (2) **likely** — `MyBookingsView` is `IsAuthenticated` but filters bookings by an email query parameter any authenticated user can supply, allowing horizontal access to another customer's booking history. (3) **confirmed** — no test exercises the real HMAC branch; the mock-order prefix bypasses it in every existing test case.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The HMAC verification path in `PaymentVerifyView` has a gap: when `RAZORPAY_KEY_SECRET` is not set, `os.environ.get('RAZORPAY_KEY_SECRET', '')` silently returns an empty string. The HMAC is computed with an empty key and compared against whatever the caller supplies. Because the empty-key HMAC of a known message is deterministic, an attacker who can observe a real Razorpay order ID can pre-compute the expected digest and confirm a booking without paying. The `mock_order_` bypass is safe — it only fires for order IDs generated locally when credentials are absent — but the guard needs to extend to the case where `RAZORPAY_KEY_ID` is set but `RAZORPAY_KEY_SECRET` is not.

`MyBookingsView` requires `IsAuthenticated` but filters bookings by a `customer_email` query parameter any logged-in user can supply. Any authenticated user can read another person's full booking history, seat details, and payment status by substituting a different email — horizontal privilege escalation in one request. The existing `test_my_bookings_returns_only_own` test logs in and queries with the user's own email; it does not assert that querying a different email is rejected.

The Checkout page encodes test-mode state as `"__TEST_MODE__:<order_id>:<booking_ref>"` in the `error` state field. `simulatePayment` extracts values by `error.split(":")` at indices 1 and 2. Any code path that resets `error` (the catch block does `setError(data?.error || ...)`) destroys the test-mode context, leaving `parts[1]` and `parts[2]` empty when simulate is clicked.

No test exercises the real HMAC branch. All 18 tests use `mock_order_` IDs, so the `hmac.compare_digest` path is never reached.

<summary>Issues (4)</summary>

1. **HMAC bypass with missing secret** — When `RAZORPAY_KEY_SECRET` is not in the environment, the signature check runs with an empty-string key, producing a deterministic expected HMAC. An attacker with a valid real order ID can pre-compute this value and confirm a booking without paying. Guard with `if not secret: return Response({"error": "Payment not configured"}, status=500)` before the HMAC call, or fall back to the mock path explicitly.

2. **Horizontal privilege escalation on /api/bookings/my/** — `IsAuthenticated` only proves the caller has a session; it does not prove the caller owns the email they query. Any authenticated user can pass `?email=victim@example.com` and read the victim's full booking history. Filter by `request.user.email` or validate that `request.user.email == email` before returning results.

3. **HMAC path not tested** — Every test in the suite uses a `mock_order_` prefix, so the real HMAC branch is never exercised. Add a test that constructs a valid HMAC signature with a known test secret, sets `RAZORPAY_KEY_SECRET` via `override_settings`, sends a non-mock order ID, and asserts it confirms. Also add a test that sends a wrong signature and asserts 400.

4. **Checkout test-mode state coupling** — `simulatePayment` extracts `order_id` and `booking_ref` by splitting the `error` state string on `:`. Introduce a dedicated piece of state (e.g. `testModeData: { orderId, bookingRef } | null`) instead of encoding data into the error string to eliminate the fragile parsing and the accidental render of `parts[2]` as an empty string if the UUID contains no extra segments.

## HMAC verification gap when secret is absent

`PaymentVerifyView.post` checks `is_mock = razorpay_order_id.startswith("mock_order_")`. For a real Razorpay order ID (e.g. `order_KZfERk...`) it proceeds to the HMAC branch:

```python
secret = os.environ.get("RAZORPAY_KEY_SECRET", "")
msg = f"{razorpay_order_id}|{razorpay_payment_id}".encode()
expected = hmac.new(secret.encode(), msg, hashlib.sha256).hexdigest()
if not hmac.compare_digest(expected, razorpay_signature):
    return Response({"error": "..."}, status=400)
```

When the env var is absent, `secret` is `""` and `expected` is a fixed, predictable hex string. Any caller who submits `razorpay_signature=<precomputed value>` with a real order ID passes verification without payment. The fix is a one-liner before the HMAC computation: `if not secret: return Response({"error": "Payment verification not configured."}, status=500)`. The mock-order path already handles the legitimate "no credentials" case cleanly.

## Horizontal access on MyBookingsView

```python
class MyBookingsView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request):
        email = request.query_params.get("email", "").strip()
        queryset = Booking.objects.filter(customer_email=email)...
```

The existing TODO comment acknowledges the design debt (`TODO: replace email query param with session auth`). Until that's addressed, the minimum fix is `if email != request.user.email: return Response(status=403)`. The test in `test_auth.py` checks that email1's results don't contain email2's bookings, but it does so by logging in as a regular user and querying with their own email — it doesn't assert that querying with a *different* email is rejected.

## Checkout test-mode state management

When `razorpay_key_id` is empty, the component does:

```js
setError("__TEST_MODE__:" + razorpay_order_id + ":" + booking_reference);
```

Then `simulatePayment` calls `error.split(":")` and accesses `parts[1]` and `parts[2]`. If `razorpay_order_id` ever contains a colon (some Razorpay test IDs do not, but the shape is not guaranteed), `parts[2]` would be empty. Beyond correctness, using the error field as a data carrier means any re-render path that clears `error` (e.g., the network-error catch) would destroy the test-mode state. The fix is a separate `testModeData` state object.

## Test coverage

18 tests cover seat generation/idempotency, hold conflict detection, expired hold release, cross-cinema seat validation, full booking creation, mock-payment confirmation, cancel-releases-seats, double-cancel idempotency, PDF content-type, PII exclusion on the verify endpoint, and admin/generate auth gating. The conspicuous gap is the real HMAC path: no test exercises the branch where `is_mock` is false. This means the confirmed HMAC-bypass bug above would not be caught by CI even after a fix is applied, unless the test is added.

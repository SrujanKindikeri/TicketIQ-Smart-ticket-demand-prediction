# TicketIQ complete cinema booking system

This change adds the full end-to-end cinema booking system on top of the existing TicketIQ skeleton. The backend gains three new models (Payment, BookingSeat, extended Booking), 13 new API endpoints, Razorpay payment integration with HMAC-SHA256 signature verification, PDF ticket generation with QR code, and 21 tests covering the seat/availability/booking/auth/ticket surface. The frontend gains 7 new React pages wired into a 5-step booking flow state machine (movie → showtime → seat → checkout → confirmation), plus admin and customer booking history pages. Existing endpoints are preserved; migrations applied cleanly.

**Watch for:** The `MyBookings` page (`/api/bookings/my/`) is guarded by `IsAuthenticated` on the backend but the frontend sends no auth credentials — every real user will get a 401/403 at runtime (confirmed). `BookingDetailSerializer` uses `fields = "__all__"` and inherits customer PII (`customer_email`, `customer_phone`, `customer_name`) into the admin list endpoint and the customer's own history endpoint — the former is intentional, the latter is redundant since the user already supplied the email to query. The `SeatSelection` multiplier table (`{Silver:1.0, Gold:1.5, Premium:2.0}`) is hardcoded in the frontend and diverges from the actual per-seat `price_multiplier` stored in the database; total amounts shown in the UI can differ from what the backend charges.

**Verdict**: NEEDS_CHANGES

---

## High-level view

Payment security was an open issue in a prior pass and has been fixed: `PaymentVerifyView` now returns 500 when `RAZORPAY_KEY_SECRET` is absent rather than computing an HMAC over an empty key, and the HMAC path is exercised by three new test cases. The cancel action rolls back `show.tickets_booked` and deletes `BookingSeat` rows; note that cancellation is admin-only (`IsAdminUser`), so the "Cancel" button in `MyBookings.jsx` will always get a 403 for non-staff users — compounding the auth gap described below.

The `MyBookings` page is broken at runtime because the endpoint requires Django session authentication (`IsAuthenticated`) but the React component makes an unauthenticated `axios.get` with no credentials. The backend will return 403 for every real visitor. This is not a subtle edge case — the feature is non-functional for anyone who hasn't already obtained a session cookie through the Django admin.

The `SeatSelection` and `Checkout` pages compute seat prices using a hardcoded JavaScript multiplier map `{Silver:1.0, Gold:1.5, Premium:2.0}` rather than the prices returned by the availability endpoint. The API already returns the correct `price` per seat; the frontend ignores it. This creates a visible discrepancy: a cinema that configures a Gold seat at 1.3× will show the wrong total in the UI while the backend charges the correct 1.3× amount.

The `/verify/` endpoint correctly strips PII. `BookingDetailSerializer` uses `fields="__all__"` which exposes `customer_email` and `customer_phone` through `AdminBookingsView` (acceptable for staff) and `MyBookingsView` (redundant but not a security gap since the user proved ownership via the email match). No cross-customer data is accessible.

The 21 tests cover the main happy paths and several key security branches. The hold expiry cleanup side-effect is verified via the availability endpoint. What's missing: no test for `TicketView` with an unconfirmed booking, no test verifying that `HoldSeatsView` rejects an empty `seat_ids` list, and no test covering the `DELETE` hold release path.

## MyBookings auth gap

`MyBookingsView` has `permission_classes = [IsAuthenticated]`. The privilege-escalation fix (email must match `request.user.email`) is correct and tested. However, `MyBookings.jsx` calls `axios.get(\`${API}bookings/my/?email=...\`)` with no `withCredentials: true` and no `Authorization` header. The browser will not send the Django session cookie cross-origin without explicit opt-in, and no token exchange exists in the booking flow. Every real user hitting this page gets a 401 or 403 — confirmed by the absence of any credential-passing code in the component. The fix is either to pass `withCredentials: true` (and ensure CORS is configured to allow it) or to relax the permission to `AllowAny` given the email-ownership check already enforces isolation.

## Price display vs. backend charge discrepancy

`ShowAvailabilityView` already computes `price = show.ticket_price * seat.price_multiplier` for each seat and returns it in the `price` field of every seat object. `SeatSelection.jsx` ignores this field and recomputes the total using its own static map:

```js
const CATEGORY_MULTIPLIER = { Silver: 1.0, Gold: 1.5, Premium: 2.0 };
const total = selected.reduce((sum, seat) => {
  const mult = CATEGORY_MULTIPLIER[seat.category] || 1.0;
  return sum + basePrice * mult;
}, 0);
```

`Checkout.jsx` has an identical copy. Any cinema that assigns non-standard multipliers to its seats will show a different amount in the UI than the backend will charge. The fix is to replace `basePrice * CATEGORY_MULTIPLIER[seat.category]` with `Number(seat.price)` using the value already in the seat object.







## Test coverage shape

21 tests pass in ~10 seconds. The HMAC branch, the double-cancel path, the cross-user 403, the expired-hold cleanup, and the foreign-seat rejection are all covered. Gaps: `TicketView` is only tested on a confirmed booking; the behavior with a pending or cancelled booking is unspecified and untested. The `DELETE /api/shows/<id>/hold/` path has no test. `HoldSeatsView`'s input validation (empty list, non-list body) returns 400 per code but has no test.
